# Persona Wire 全体像 — 画面・DB・外部連携、収集と AI 判定、記事のステータス

第1段階（H1、H2、H6）に着手する前に、アプリ全体の構造を整理した文書です。画面とコードの細かい対応は [SCREENS.md](SCREENS.md)、DB の定義は [DB.md](DB.md) を参照してください。行番号は 2026-10-27 時点の素の JavaScript 版（`assets/js/`）に基づきます。

## 0. 全体の流れ

```
                    ┌──────────────┐
                    │ ④ ペルソナ    │  読者像と判定基準を決める
                    └──────┬───────┘
                           │ 判定基準
 [外部] ニュース/SNS ──収集──▶ ┌──────────────┐ ◀──判定── [外部] AI (LLM)
                           │ ② 収集・AI判定 │  人が採用・公開・却下を決める
                           └──┬────────┬──┘
                    公開中の記事 │        │ 採用済み・公開中の記事
                              ▼        ▼
 ┌────────────┐      ┌────────────┐  ┌────────────┐
 │ ⑤ 商品・リンク│ ───▶ │ ⑦ 公開サイト │  │ ③ 有料配信   │ ──送信──▶ [外部] メール/LINE
 └────────────┘ 商品  └────────────┘  └────────────┘ ◀─課金── [外部] 決済
        │        └──────── PR枠 ─────────────▲
        ▼
  [外部] ASP（成約データ）

 ① ダッシュボード … 上のすべてを集計して表示するだけ（自分では何も作らない）
 ⑥ Notion連携    … 記事・スコア・ペルソナ・配信号を [外部] Notion と同期
```

中心にあるのは **④ペルソナ** と **②記事** です。ほかの画面は、この 2 つを使う側です。

DB の表名は [DB.md](DB.md) の設計案のものです。今のアプリは、これらをすべてブラウザ内の 1 つのデータ（localStorage）で代用しています。

## 1. 画面ごとの機能と DB

各画面が主に書き込む表、つまりその画面がデータの「持ち主」になる表です。

| 画面 | 主な機能 | 持ち主になる DB 表 |
|---|---|---|
| ① ダッシュボード | KPI、7日間のグラフ、ペルソナ別状況、配信予定、アクティビティを表示する | なし（読むだけ） |
| ② 収集・AI判定 | 収集の実行、絞り込み、スコアの確認、採用・公開・却下、再判定、編集コメント | `articles`、`article_persona_scores` |
| ③ 有料配信 | プランの追加・編集・停止、配信号の作成・編集・予約・送信、メールのプレビュー | `plans`、`issues`、`issue_articles`（将来 `subscribers`、`subscriptions`、`email_events`） |
| ④ ペルソナ | 読者像、関心キーワード、NG ワード、トーン、しきい値の設定。有効・無効 | `personas` |
| ⑤ 商品・リンク | アフィリエイト商品の登録、対象ペルソナの指定、計測リンクのコピー | `products`、`product_personas`（将来 `link_clicks`、`conversions`） |
| ⑥ Notion連携 | 接続・解除、同期の実行、同期設定、DB とプロパティの対応づけ | `notion_connections`、`notion_database_mappings`、`notion_property_mappings`、`notion_sync_logs` |
| ⑦ 公開サイト | 公開中の記事をペルソナ別に表示（いまはプレビュー）。非公開に戻す | なし（読むだけ。非公開に戻す操作だけ `articles` を書き換える） |
| 全画面共通 | ログイン（まだ無い。H2）、操作の記録 | `users`、`activity_logs` |

## 2. 画面をまたぐ機能と DB

ある画面の操作が、別の画面に影響する部分です。

| つながり | 書く画面 → 読む画面 | 使う DB 表 | 具体的に起きること |
|---|---|---|---|
| ペルソナが判定基準になる | ④ → ② | `personas` → `article_persona_scores` | しきい値を変えると、要確認の記事が判定し直される（[personas.js:35](../assets/js/views/personas.js#L35)）。無効にしたペルソナは判定から外れる |
| ペルソナが全画面の分類軸になる | ④ → ②③⑤⑦① | `personas` | 記事の主担当、プランの対象、商品の対象、公開サイトのタブ、ダッシュボードのペルソナ別表示がすべてペルソナ単位 |
| 記事の公開 | ② → ⑦ | `articles.status = published` | 公開中にすると公開サイトに出る（[site.js:11](../assets/js/views/site.js#L11)）。⑦で非公開にすると、②では採用済みに戻る |
| 記事を配信に使う | ② → ③ | `articles.status`、`issue_articles` | 採用済み・公開中の記事が配信号の候補になる（[delivery.js:84](../assets/js/views/delivery.js#L84)）。②から直接配信号に追加することもできる |
| 編集コメント | ② → ⑦③ | `articles.comment` | ②で書いたひとことが、公開サイトと配信メールに表示される |
| 商品の差し込み | ⑤ → ⑦③ | `products`、`product_personas` | 有効な商品が、公開サイトの「おすすめ」（3件）と配信メールの PR 枠（1件）に、対象ペルソナに合わせて出る |
| 購読の呼びかけ | ③ → ⑦ | `plans` | 対象ペルソナの配信中プランが、公開サイトに購読の案内として出る |
| 集計 | ②③⑤ → ① | `articles`、`plans`、`issues`、`products`（将来 `link_clicks`、`subscriptions`） | 収集数、採用候補、購読者数、売上、クリック数、配信予定を集めて表示する |
| 操作の記録 | 全画面 → ① | `activity_logs` | 採用・公開・予約などの操作がアクティビティに出る |
| 同期状態 | ⑥ → サイドバー | `notion_connections`、`notion_sync_logs` | 最終同期の時刻がサイドバーに出る |
| ペルソナ削除の影響 | ④ → ②③⑤ | 各表の `persona_id` | 記事のスコア・主担当と商品の紐づけから外れる。プランは残ってしまう（M5 の課題） |

## 3. 外部との連携

今のアプリでは、外部とはどれもつながっていません（すべてシミュレーション）。本番で必要になる連携先は次のとおりです。

| 連携先 | 何をするか | 関係する画面 | 関係する DB 表 | 今の状態 | 段階 |
|---|---|---|---|---|---|
| ニュース RSS・SNS API（YouTube、note、X、Threads） | 記事・投稿を定期的に取ってくる | ② | `articles`（+ 提案中の `sources`） | サンプル14件から乱数で生成 | 第2（H3） |
| AI（LLM） | 記事とペルソナの適合度を採点し、理由を付ける | ②④ | `article_persona_scores` | 固定値に乱数を足すだけ | 第2（H4） |
| Notion API | 記事・スコア・ペルソナ・配信号を Notion の DB と同期する | ⑥（データは②③④） | Notion の4表、`articles.notion_page_id` | 進捗バーが動くだけ | 第3（H5） |
| メール配信 / LINE | 配信号を購読者に送り、開封を記録する | ③ | `issues`、`email_events` | 状態が「配信済み」に変わるだけ | 第4（M1） |
| 決済（Stripe など） | 月額課金、購読者の増減、解約 | ③① | `subscribers`、`subscriptions` | 購読者数・売上は固定値 | 第4（M2） |
| ASP（A8.net など） | 成約データを取り込む | ⑤① | `conversions` | 成約数は固定値 | 第4（M3） |
| 計測リンク `/go/<ID>` | クリックを記録してショップへ転送する。外部ではなく自前のサーバーで作る | ⑤⑦③ | `link_clicks` | 転送先がまだ無い | 第4（M3） |

外部連携は、どれもサーバー側で動かす必要があります。API キーやトークンをブラウザに置けないことと、定期実行が必要なことが理由です。第1段階でサーバーを用意すること（H1）が、これらすべての前提になります。

## 4. 収集と AI 判定

この製品の「AI収集」は、実際には **収集**（H3）と **AI判定**（H4）の 2 段階です。

### 今の動き

- **収集:** `store.collect()`（[store.js:188](../assets/js/store.js#L188)）が、固定のサンプル14件（`ITEM_POOL`、[store.js:23](../assets/js/store.js#L23)）からランダムに 3〜5 件を選んでいるだけです。URL も `example.com/article/<乱数>` で、同じ記事が何度も入ります。
- **AI判定:** 各ペルソナのスコアは、固定値に ±8 程度の乱数を足したものです。`judge()`（[store.js:11](../assets/js/store.js#L11)）は、その中で最高点のペルソナを主担当にします。しきい値以上なら採用推奨、しきい値 −20 以上なら保留、それ未満は除外です。ペルソナのキーワードと NG ワードは判定に使っていません。

### 本物にした場合の流れ

```
[定期実行 (例: 30分ごと)]
   │
   ▼
① 取得       RSS / 各SNSのAPI から新着を取る
   ▼
② 正規化     タイトル・要約・URL・日時・ソースを共通の形にそろえる
   ▼
③ 安全確認   http(s) 以外の URL は捨てる（H6）
   ▼
④ 重複除外   URL が既に articles にあれば捨てる（DBのユニーク制約）
   ▼
⑤ ルール選別 NGワードに当たる記事は除外し、LLMに渡さない（費用の節約）
   ▼
⑥ LLM判定    1記事につき1回の呼び出しで、5ペルソナ分の
             スコアと理由をまとめて JSON で返させる
   ▼
⑦ 保存       articles（status=pending）と article_persona_scores へ書き込む
   ▼
⑧ 人が確認   収集・AI判定の画面で、採用・却下・公開を決める
```

AI が使われるのは ⑥ だけです。① から ⑤ は普通のプログラムで処理します。

### ソースごとの注意点（要確認）

料金や制限は変わりやすいため、着手前に各社の最新情報を確認してください。

| ソース | 取得方法 | 注意点 |
|---|---|---|
| ニュース | RSS（多くは無料） | 本文の転載は著作権の問題になる。保存と表示はタイトル・要約・リンクに留める |
| YouTube | YouTube Data API | 無料枠は 1 日 10,000 ユニット。検索は 1 回 100 ユニットかかるため、チャンネル指定で取る方が節約になる |
| note | クリエイターごとの RSS | 公式 API は無い。追うアカウントを決めて登録する |
| X | 公式 API | 読み取りには有料プランが必要で、比較的高額 |
| Threads | 公式 API | 他人の投稿の取得や検索には制限がある |

## 5. 収集先（どこから収集するか）

### 現状

決まっているのはソースの**種類**（NEWS、YOUTUBE、NOTE、X、THREADS）だけです。サンプルの媒体名は架空です。「どの RSS を読むか」「どのチャンネルやアカウントを追うか」という**収集先の一覧はどこにもありません**。DB 設計にも収集先の表がなく、`articles.source_name`（媒体名の文字列）があるだけです。H3 の前に埋める必要があります。

### 収集先の決め方

| 方式 | 中身 | 向いているもの |
|---|---|---|
| A. 登録したソースを巡回する | RSS・チャンネル・アカウントを一覧に登録し、新着を定期的に取る | RSS、YouTube、note。品質を管理しやすい |
| B. キーワードで検索する | ペルソナの関心キーワードで各サービスを検索する | ニュース全般、X、Threads。新しい情報源を見つけやすいが、ノイズと API 費用が増える |

始めは **A を中心にし、ニュースだけ B を足す** のがおすすめです。ニュースのキーワード検索は、Google ニュースの検索 RSS（`news.google.com/rss/search?q=キーワード`）で無料で試せます（利用規約は要確認）。

### ペルソナ別の収集先のイメージ

| ペルソナ | ニュース | SNS |
|---|---|---|
| P01 テック × 投資 | テック・経済系メディアの RSS、「半導体」「資金調達」で検索 | 決算・半導体解説の YouTube チャンネル |
| P02 筋トレ・食事 | 生活・健康系メディアの RSS | 宅トレ系 YouTube、自炊・節約系 note |
| P03 子育て・共働き | 行政・社会面の RSS、「保育」「育休」で検索 | 共働き家庭の note、Threads |
| P04 一人暮らし・節約 | 生活・マネー系メディアの RSS | 節約系 note、暮らし系 YouTube |
| P05 地方・移住 | 地域経済ニュース、自治体の発表 | 移住者の note、地域の YouTube |

実際の収集先は運営者が選びます。信頼性、更新頻度、規約上取得してよいかを確認してください。

### 設計への反映案：`sources` 表

| 列 | 例 |
|---|---|
| `kind` | `NEWS` / `YOUTUBE` / `NOTE` / `X` / `THREADS` |
| `method` | `rss`（巡回）/ `search`（キーワード検索） |
| `target` | RSS の URL、チャンネル ID、検索キーワードなど |
| `persona_ids` | 主に狙うペルソナ（判定のヒントにも使える） |
| `active` / `last_fetched_at` | 停止中かどうか、最後に取得した日時 |

`articles` に `source_id` を持たせれば、収集先ごとの採用率を集計でき、採用率の低い収集先を外す改善につなげられます。管理画面には「収集先」画面を足します。

## 6. 記事のステータス

### AI 判定とステータスの違い

| 項目 | 誰が決めるか | 値 | 役割 |
|---|---|---|---|
| `verdict`（AI判定） | AI が自動で | 採用推奨 / 保留 / 除外 | 人が判断するときの参考情報 |
| `status`（ステータス） | 人が手で | 要確認 / 採用済み / 公開中 / 却下 | 記事が実際にどこで使われるかを決める |

AI が採用推奨と判定しても、ステータスは自動では変わりません。収集した記事はすべて要確認から始まります（[store.js:199](../assets/js/store.js#L199)）。

### 状態の移り方

```
            収集
             │
             ▼
        ┌─────────┐   採用する    ┌─────────┐  公開サイトへ公開  ┌─────────┐
        │ 要確認   │ ───────────▶ │ 採用済み │ ────────────────▶ │ 公開中   │
        │ pending │ ◀─────────── │ approved│ ◀──────────────── │published│
        └─────────┘  要確認に戻す  └─────────┘    非公開に戻す     └─────────┘
             │                         │                           │
             └──────── 却下 ───────────┴───────────────────────────┘
                                       ▼
                                  ┌─────────┐
                                  │ 却下     │  （削除はされない。要確認に戻せる）
                                  │ rejected│
                                  └─────────┘
```

### 各ステータスで起きること

| ステータス | 意味 | この状態だと起きること |
|---|---|---|
| 要確認 | 人がまだ見ていない | サイドバーの件数バッジに数えられる（[app.js:16](../assets/js/app.js#L16)）。ダッシュボードの「AI採用候補」に出る（AI が採用推奨のもの、[dashboard.js:32-33](../assets/js/views/dashboard.js#L32-L33)）。しきい値を変えると、この状態の記事だけ再判定される。公開サイトにも配信にも出ない |
| 採用済み | 使うと決めたが、まだ公開していない | 配信号に載せる候補になる。新しい配信号を作ると、そのペルソナの採用記事が最大 3 件自動で入る（[delivery.js:46](../assets/js/views/delivery.js#L46)）。公開サイトには出ないので、「有料読者だけに届ける記事」として使える |
| 公開中 | 無料の公開サイトに出している | 公開サイトに表示され、編集コメントも出る。配信号の候補にもなる |
| 却下 | 使わない | どこにも出ない。絞り込みで「却下」を選べば見られ、あとから戻せる |

採用済みと公開中の違いは、**無料の公開サイトに出すかどうか**です。どちらも有料配信には使えます。

### 今の実装の穴

1 と 2 は、TypeScript 版で修正済みです（`store.setItemStatus()`、2026-10-28）。素の JavaScript 版には残っています。

1. **却下や要確認に戻しても、配信号からは外れない。** 配信号の `itemIds` に残るため、却下した記事がそのまま送られる（`setStatus()`、[inbox.js:164-171](../assets/js/views/inbox.js#L164-L171)）。
2. **要確認や却下の記事でも、収集・AI判定の画面から配信号に追加できる。** 配信画面の候補は採用済み・公開中に絞っているが、`addToIssue()`（[inbox.js:182-188](../assets/js/views/inbox.js#L182-L188)）には状態の確認がない。
3. **誰が変えたかが残らない。** アクティビティには操作者が記録されない。

## 7. 第1段階（H1、H2、H6）への反映

| 項目 | この文書から決まること |
|---|---|
| H1 サーバーと DB | 最初は `users`、`activity_logs`、`personas`、`articles`、`article_persona_scores` で十分（[DB.md](DB.md) 9章）。`sources` も最初から入れておくと第2段階がそのまま進められる。サーバーは**定期実行**と**秘密情報の保管**ができるものを選ぶ（例: Supabase の Edge Functions と pg_cron）。`status` の 4 値だけを許す制約を入れ、6章の穴 1・2 はサーバー側のルールで防ぐ |
| H2 ログインと権限 | 編集者は要確認・採用済み・却下の変更まで。公開中への変更と取り消し、配信の送信、Notion の接続解除は管理者だけにする。収集と判定は自動処理が行うため、`activity_logs` の実行者に「システム」を入れられるようにする |
| H6 URL の安全確認 | 表示時（②の元記事リンク、⑦）に加えて、収集の取り込み時にも `http(s)` 以外を弾く。DB の `articles.url` にも同じ制約と重複不可の制約を入れる |

### 先に決めておくこと

- DB をどこで動かすか、ログインの方法（[DB.md](DB.md) 10章の 1・2）
- 最初に対応する収集先（費用と手間から、ニュースの RSS と YouTube から始めるのがおすすめ）
- 収集の頻度と、1 日に判定する記事数の上限（LLM の費用はここで決まる）
- 使う LLM
