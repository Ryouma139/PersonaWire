## 2. 主な変更（大きいものから）

### 2.1 データをブラウザから Supabase に移した（H1）

- ペルソナ・記事・スコア・操作ログは Supabase の表から読み、画面の操作は表に書き込む（`ts/src/db.ts`）。
- 書き込みが権限ルールで拒否されたら、エラーを出して DB の内容に戻す（`store.commit()`）。
- 有料配信・商品・Notion 連携の画面は、まだブラウザ保存のサンプル（第3・第4段階で移す）。
- 乱数で偽の記事・スコアを作っていた「収集を実行」「再判定」は削除した。

### 2.2 ログインと権限（H2）

- メールアドレス（パスワード、またはメールのリンク）でログインする（`ts/src/auth.ts`）。
- 初めてログインした人は「未承認」で、中は見られない。管理者が `users.role` を付けると使える。

| 操作 | 未承認 | 編集者 | 管理者 | 自動処理（バッチ） |
|---|---|---|---|---|
| 記事・ペルソナを見る | × | ○ | ○ | ○ |
| 採用・却下・コメント・記事の追加と編集 | × | ○ | ○ | ○ |
| 公開・非公開の切り替え、記事の削除 | × | × | ○ | ○ |
| ペルソナ・収集先・役割を変える | × | × | ○ | ○ |

権限は DB の中（RLS とトリガー）で守る。画面のボタンを隠すのは使いやすさのためで、守りの本体ではない。

### 2.3 外部 URL の安全確認（H6）

- 画面では `ui.safeUrl()` を通し、`http(s)` 以外（`javascript:` など）はリンクにしない。
- DB の `articles.url` にも `http(s)` だけを許す制約がある。収集バッチも取り込む前に弾く。

### 2.4 収集バッチ（H3）

| 収集先 | 方法 | 1 回に取り込む数 |
|---|---|---|
| Notion news_link | 親ページ → 日付ページ → 記事一覧をたどる（直近 3 日分） | すべて |
| YouTube 5 チャンネル（PIVOT、ほしみみ、学識サロン、筋トレ大学、よし移住しよう） | チャンネルの RSS | 各 2 本 |
| note #投資・#筋トレ・#子育て・#節約・#移住 | ハッシュタグの RSS | 各 2 件 |
| note 注目記事 | RSS | 停止中（ハッシュタグに切り替えた） |

- 実行: 2 時間ごと（日本時間の 0:00、2:00 … 22:00）。管理画面の「今すぐ収集」でも動く。
- 1 日の上限: 全収集先の合計で 100 件（日本時間の 0 時で数え直す）。漏れた記事は翌日以降に拾う。
- 取り込まない記事: `http(s)` 以外の URL、除外カテゴリ（芸能・文化）、全ペルソナ共通の NG ワード（芸能）、登録済みの URL、削除済みの URL。
- 優先順位: 収集先の区別はなく、収集日時の新しい順。
- 種別（kind）: URL のドメインから決める（youtube.com → YOUTUBE、note.com → NOTE など。それ以外は NEWS）。
- 仮の主担当: カテゴリとペルソナの対応（`sources.options.category_personas`）で決める。
- 記録: 実行ごとに `collect_runs`、登録・削除があれば操作ログ（実行者は「システム」）。

### 2.5 却下した記事の自動削除

- 状態が「却下」で、最後の更新から 5 日たった記事を、収集バッチの最後に削除する（スコアも一緒に消える）。
- 削除した URL は `purged_urls` に残し、同じ記事を取り込み直さない。
- 日数は `collector/wrangler.jsonc` の `PURGE_REJECTED_DAYS`（管理画面の表示用の `PURGE_DAYS` も合わせる）。

### 2.6 公開と自動デプロイ

- 管理画面と収集バッチを、Cloudflare Workers に公開した。
- GitHub と Cloudflare を Workers Builds でつないだ。`main` にプッシュすると、変更があったフォルダ（`ts/` か `collector/`）の Worker だけが自動でデプロイされる。GitHub Actions は使っていない。
- 管理画面の接続先（公開してよい値）は `ts/.env.production` に書き、Git に入れている。

## 5. 運用の決まり

| 決まり | 理由 |
|---|---|
| **DB の変更を含むときは、SQL を先に実行してからプッシュする** | プッシュするとすぐ新しいコードが公開され、まだ無い表や列を読みに行って壊れる |
| 収集先の追加・停止は `sources` 表で行う（プッシュ不要） | 次の実行からすぐ反映される |
| 秘密情報（Supabase の Secret key、Notion のトークン）は Cloudflare の Secrets と `collector/.dev.vars` だけに置く | Git や管理画面に置くと漏れる |
| 設定の正本は `wrangler.jsonc` | ダッシュボードで変えても、次のデプロイで上書きされる |
| コードの正本は GitHub | Cloudflare の「Edit code」で直さない |
| 使わない記事は削除ではなく却下する | 削除すると、同じ記事がまた取り込まれる（却下は 5 日後に自動で削除し、URL を記録する） |

## 6. 起きた問題と、そこから決めたこと

| 問題 | 原因 | 対応 |
|---|---|---|
| 公開した管理画面が「読み込み中…」で止まった | 接続先を `.env.local`（Git に入らない）にだけ書いていて、Cloudflare の自動ビルドに入らなかった | `ts/.env.production` を Git に入れた。接続先が無いときは画面に理由を出すようにした |
| YouTube が 2 本ずつではなく、まとめて 66 本入った | 2 本に絞る処理を公開する前に、YouTube の収集先を登録した | 必要なら古い要確認の動画を消す SQL を用意した。順番（コードの公開 → 収集先の登録）を決まりにした |
| 手元のバッチが秘密情報を読めなかった | wrangler は起動中に `.dev.vars` を読み直さない | `.dev.vars` を変えたら `npm run dev` を起動し直す |
